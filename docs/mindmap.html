Outbound BDR hackathon — thought process

How I broke the problem down

Input is a campaign brief (LatAm mining, anchored on SQM). Output is an account list, a contact list, and personalised outreach. The interesting question is not can an LLM write this — it is how do you decompose the job so that every claim is checkable and every failure is visible.

1 · The framing question

What does a human BDR actually do before they send one good email?

They build a mental model of the anchor account. They find lookalikes. They cut the ones that don't fit. They read the news on each survivor. They work out which recent event makes now the moment. They find who owns that problem. They sanity-check the facts. They write. Then they re-read it and rewrite the weak bits.

That is nine distinct jobs, not four. Collapsing them into one prompt is the thing that produces generic output — so I gave each job its own agent, its own instructions, and its own failure mode.

Naive split

4 stages

Accounts → Contacts → Research → Emails. Matches the brief's headings, but each stage is doing three jobs at once and none of them can be checked independently.

What I built

9 specialists

Every agent has one job, typed input, typed output. A weak stage is identifiable and swappable without touching the others.

Why it matters

Checkability

Separating research from verification from writing is what lets a fact guard sit between them and quarantine unsourced claims.

2 · The pipeline

Input

Campaign brief

Target vertical + reference account + goal titles + our angle. One object, no other input.

→ CampaignBrief

A0

ICP Architect

Researches SQM and deconstructs it into a weighted, machine-readable ICP — 6–8 scored axes plus hard disqualifiers. Everything downstream scores against this contract.

brief → ICP{dimensions[], weights, disqualifiers[]}

A1

Account Scout

Grounded search for real LatAm operators matching the profile. Deliberately over-fetches (target + 6) so the next stage has something to cut.

ICP → Account[] candidates + source URLs

A2Decision

Account Qualifier

Scores every candidate on every ICP axis, computes a weighted fit score, and applies the disqualifiers. This agent is allowed to say no.

candidates → qualified[] + rejected[]

qualified ↓  ·  rejected →
Kept, not discarded

Rejected accounts

Shipped to the UI with the reason. The boundary of the ICP is information an AE needs — it shows the screen actually ran.

Continue

Top N by fit score

Depth over breadth. 8 well-researched accounts beat 40 shallow ones.

fan out — the next three agents run per account, independently
A3

Research Analyst

Deep grounded research per account: footprint, recent news, technology signals, HSE pressure, contractor usage. Emits atomic claims, not a prose blob — so verification can happen per claim instead of per brief.

Account → Claim[]{text, confidence, sources[]}

A4

Signal Extractor

Turns claims into dated trigger events — the reason this account should care now. This is the layer that separates strategic insight from company trivia, which is why it is its own agent.

Claim[] → Trigger[]{what happened, why it matters now, citations}

A5

Contact Mapper

Finds Head of Ops / VP HSE / Site Directors, including local-language equivalents. Highest hallucination risk in the pipeline, so it is instructed to return nothing rather than guess, and every email carries a found / inferred / not-found status.

Account → Contact[]{name, title, linkedin, email_status, sources[]}

A6Gate

Verifier / Fact Guard

Deterministic Python, not an LLM call. A guard implemented as another model can hallucinate its own approval. Any claim without a resolvable source URL is quarantined before it can reach an email.

Claim[] → verified[] + quarantined[] (both surfaced)

verified ↓  ·  unsourced →
Blocked

Quarantine

Never reaches an email. Listed in the run trace with the reason, so the gap is visible instead of silently filled in.

Continue

Verified material only

The composer physically cannot cite a quarantined claim.

A7

Message Composer

One email per contact from verified material. Picks one FlytBase proof point that actually maps to the account (Anglo American → mining major, Shell → hazardous 24/7 process, CSX → sprawling linear sites) rather than name-dropping all three. Also emits a call opener and objection prep.

verified claims + trigger + contact → Email

A8Reflection loop

Critic

Two layers. Deterministic gate: placeholder detection, length, banned filler — these are the brief's disqualifiers, so they cannot depend on a model's opinion. Rubric scoring: specificity, trigger use, proof-point fit, human voice, CTA. Below the pass mark, it sends the draft back for one rewrite.

Email → score + notes → (rewrite once) → Email

pass ↓  ·  fail ↺ back to A7
Output

BDR workspace + run trace

A single results.json renders the live site: ranked accounts, ICP breakdown, cited research, contacts, emails, call openers, objections — plus every stage that succeeded, degraded, or failed.

3 · Decision points

WhereThe decisionWhat happens on each branch
A2 QualifierDoes this account clear the ICP? No → rejected list with the reason, still shipped. Yes → ranked by weighted score, top N continue.
A4 SignalsIs there a dated trigger? No → flagged; the email falls back to weaker profile-based personalisation and the account is a deprioritisation candidate.
A5 ContactsCan I verify a real person? No → return zero contacts. Never invent a name. Routed to a paid contact provider in the production fix.
A6 VerifierDoes this claim resolve to a live source? No → quarantined, logged, and made unusable by the composer.
A8 CriticDoes the draft clear the rubric? No → one rewrite with specific instructions, then re-checked.

4 · Design decisions and tradeoffs

Core  Nine narrow agents instead of one wide prompt

Each agent has one job and a typed contract with the next. A weak stage can be swapped without touching the rest, and a failure is attributable to a specific agent rather than to "the AI".

Cost: more calls, more latency, more orchestration code. Worth it — a single mega-prompt cannot be debugged, only re-rolled.

Core  Provenance is a first-class type, not a prompt instruction

"Cite your sources" in a prompt is a suggestion. Making Source a required field on every claim, and putting a deterministic gate between research and writing, makes it structural. Every fact on the site links back to where it came from.

This is the direct answer to "fabricated data is an automatic disqualifier" — it turns the biggest risk into the system's main feature.

Core  The fact guard is plain Python

Every other stage is an LLM. A6 is regex and set logic on URLs. A verifier that is itself a language model can be talked into approving its own hallucination; one that checks whether a string is a resolvable non-social URL cannot.

Tradeoff  Depth over breadth — 8 accounts, not 40

The brief asks for strategic insight, not volume. Eight accounts with dated, cited triggers are more useful to an AE than forty rows of company descriptions.

Configurable via TARGET_ACCOUNTS. The constraint is free-tier rate limits, not architecture.

Tradeoff  Two providers, split by job

Gemini carries every research stage because Google Search grounding returns real, resolvable citation URLs. Groq carries the drafting and critic loop because it is fast and the loop is high-volume. Splitting also spreads free-tier quota across the run.

Cost: two failure surfaces. Mitigated by per-stage fallback and a trace that records which provider ran and how it degraded.

Known limit  Contact discovery is the weakest stage

Public leadership pages for privately-held LatAm mining operators are thin, and much of the useful data is behind LinkedIn auth. The system returns zero contacts for some accounts rather than inventing plausible ones.

Production fix: route those accounts to a licensed contact provider (Apollo / Cognism / Lusha) or a Sales Navigator seat, keeping the same verification gate so nothing enters an email unsourced.

Known limit  English-language search bias

Grounding skews to English coverage, which under-reports Spanish and Portuguese local press — exactly where LatAm mine-level operational news lives.

Fix: run A3 twice per account with localised query sets and merge on claim similarity. Skipped here for time, not for difficulty.

5 · Where a reviewer should look

QuestionWhere it is answered
Did it actually run?Run trace tab — every stage, duration, searches issued, sources returned
Is the data real?Every claim carries clickable source links; quarantined claims are shown greyed out
Did it fail anywhere?Run trace — failures are shown with a written fix, not hidden
Is the ICP arbitrary?ICP tab — weighted axes derived from SQM, with SQM's own value on each axis
Is it just a list?Each contact ships an email, a call opener, and objection prep
